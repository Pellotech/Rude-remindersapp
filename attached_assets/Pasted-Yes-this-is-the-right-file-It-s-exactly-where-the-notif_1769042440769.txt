Yes — this is the right file. ✅ It’s exactly where the notification tap / “app open” event gets dispatched, and it’s also where the extra payload is created.

Two important improvements to make here:

1) Fix hasAttachments mismatch

Right now you intentionally set:

attachments: [],


…but you still set:

hasAttachments: !!(reminder.attachments?.length),


That tells the popup code “attachments exist” even though the notification has none. It can cause confusion later (and it’s what we saw in logs before).

✅ Change it to false for notifications (since you’re not attaching them):

hasAttachments: false,


Or if you want it to mean “this reminder has attachments in the app” (not in notification), rename it to hasRemoteAttachments to avoid confusion.

2) Cold-start safety: wait for token init before dispatching popup fetch

When the app is opened by tapping a notification, your NotificationProvider immediately fetches:

apiRequest(`/api/reminders/${reminderId}`)


If the app is still booting and initAuthToken() hasn’t finished, getAuthToken() can be null for a moment and the fetch can fail.

✅ Add a short delay or “wait for token” before dispatching the event on tap.
Simplest safe version:

setTimeout(() => {
  dispatchNotificationReceivedEvent({ ... });
}, 300);


Even better is awaiting token init, but this is a low-effort fix that usually removes flaky “could not load reminder” on cold start.

Recommended patch (copy/paste)

Inside both listeners where you call dispatchNotificationReceivedEvent, wrap it:

if (extra?.reminderId) {
  console.log('📱 Dispatching notification event for full-screen popup');

  setTimeout(() => {
    dispatchNotificationReceivedEvent({
      reminderId: extra.reminderId,
      title: notification.notification.title || '',
      body: notification.notification.body || ''
    });
  }, 300);
}


And update extra.hasAttachments to false:

hasAttachments: false,
